==================================================
0) PROPOSITO DE ESTE ARCHIVO
==================================================
Este archivo define como trabajaremos el proyecto NumiCheck sin mezclar codigo,
con enfoque rapido, modular y escalable.

Regla principal del producto:
- NumiCheck SOLO valida billetes por NUMERO DE SERIE (+ denominacion).
- No valida autenticidad fisica del billete.

==================================================
1) OBJETIVO MVP (PROYECTO FUGAZ)
==================================================
Entregar MVP funcional en 10-12 horas con:
1. Login usuario social (Google y luego Facebook si entra en tiempo).
2. Pantalla principal con:
   - Escanear por camara
   - Ingresar serie manualmente
   - Subir imagen
3. Resultado binario:
   - Verde: legal en circulacion
   - Rojo: ilegal/bloqueado
4. Historial por usuario.
5. Panel admin secreto con login propio (1 correo + 1 contrasena).
6. CRUD de series ilegales en base de datos.
7. Registro de uso y seguridad minima anti-bot.

==================================================
3) REGLAS CODEX ORGANIC (NO NEGOCIABLES)
==================================================
1. Un archivo = una responsabilidad.
2. No crear archivos gigantes.
3. No meter logica de negocio en componentes UI.
4. No meter SQL directo en controladores.
5. Todo endpoint con validacion de entrada.
6. Toda accion admin deja auditoria.

Limites recomendados:
- Componente UI: max 250 lineas
- Servicio backend: max 350 lineas
- Si un modulo crece demasiado, se divide

==================================================
4) FLUJOS DEL SISTEMA
==================================================
A) Flujo Usuario
1. Login social
2. Home
3. Escanear / Manual / Subir imagen
4. Confirmacion de serie
5. Validacion
6. Resultado verde/rojo
7. Guardar historial

B) Flujo Admin
1. URL privada no obvia
2. Login admin unico
3. Dashboard (usuarios + uso)
4. Gestion de series ilegales (CRUD)
5. Auditoria de cambios

==================================================
5) MODELO DE DATOS MINIMO
==================================================
1. users
2. social_accounts
3. admin_users
4. blocked_serials
5. validations
6. admin_audit_logs
7. security_events

Regla de motor de validacion:
- Si serie normalizada existe en blocked_serials (activa y vigente) => ROJO
- Si no existe => VERDE

==================================================
6) OPTIMIZACION TECNICA CLAVE
==================================================
1. Normalizar serie antes de consultar:
   - uppercase
   - quitar espacios extras
   - guardar formato canonico
2. Indexar blocked_serials por:
   - serial_normalized
   - denomination
   - active
3. Guardar serie enmascarada en historial para privacidad.
4. Aplicar rate limit por IP y por usuario.
5. Cache corta para reglas activas (si hace falta por carga).

==================================================
7) SISTEMA DE ANIMACION (UI PRIORIDAD)
==================================================
1. Definir tokens globales (duracion, easing, escala).
2. Usar componentes motion reutilizables (no animaciones sueltas).
3. Skeletons para estados de carga en pantallas clave.
4. Estados visuales obligatorios: loading, success, error, empty.
